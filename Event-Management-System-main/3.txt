## Problems in the agent's original plan

| Original item                                                          | Problem                                                                                   | What we are doing instead                                             |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Email OTP authentication**                                           | Adds security/OTP expiry/rate-limit/delivery complexity, but gives little interview value | Use secure email/password + server-side sessions                      |
| **Separate User/Organizer authentication**                             | Duplicates auth logic unnecessarily                                                       | One `User` identity + roles                                           |
| **Generic RBAC only**                                                  | Role checking alone doesn't stop Organizer A accessing Organizer B's data                 | Add **resource-level ownership checks**                               |
| **One Registration-centric model**                                     | Payment, order, ticket and check-in have different lifecycles                             | Separate **Order → Payment → Ticket → CheckIn** concepts              |
| **“Configure capacity”**                                               | Doesn't explicitly address concurrent purchases                                           | Make **race-safe inventory allocation** a core requirement            |
| **Stripe success/failure states**                                      | Could lead to trusting browser redirects                                                  | Stripe **webhook is authoritative**                                   |
| **Idempotent payment handling mentioned but not detailed**             | Easy for an agent to implement incompletely                                               | Explicitly test duplicate webhooks + server crash/retry               |
| **Optional worker application**                                        | Can become unnecessary distributed-system complexity                                      | Keep a **simple durable outbox/job mechanism**                        |
| **Large notification system**                                          | Lots of infrastructure for little value                                                   | Basic reliable email + retry                                          |
| **Generic check-in**                                                   | QR scanning itself isn't technically interesting                                          | Make check-in **atomic + duplicate-safe**, including concurrent scans |
| **No event-level staff model**                                         | Organizer has to do everything or permissions become too broad                            | Add `EventStaff` with limited permissions                             |
| **Broad event CRUD**                                                   | CRUD isn't particularly impressive                                                        | Add **explicit event state transitions/invariants**                   |
| **Large admin functionality**                                          | Can consume time without improving engineering depth                                      | Keep admin moderation/approval/audit functionality focused            |
| **Search/filter/etc. as major functionality**                          | Product necessity, but low engineering differentiation                                    | PostgreSQL search/filter/pagination; don't over-engineer              |
| **Refund/cancellation foundation**                                     | Could easily explode into a complex subsystem                                             | Keep a clean foundation, not a full refund platform                   |
| **API documentation + monitoring + deployment all emphasized equally** | Can create “production theater”                                                           | Keep them as polish; prioritize core correctness                      |
| **No explicit concurrency tests**                                      | Happy-path tests can hide the hardest bugs                                                | Add tests for race conditions and retries                             |
| **No explicit security invariants**                                    | Agent may implement UI-level protection only                                              | Enforce validation/authorization/security **server-side**             |
| **Potential separate API + Next.js without a clear reason**            | Can create unnecessary architectural duplication                                          | One clear API architecture; no duplicated business logic              |

# New things we're adding

| New addition                            | Why we're adding it                                                |
| --------------------------------------- | ------------------------------------------------------------------ |
| **Expiring ticket holds**               | Gives you a real concurrency/time-based problem to explain         |
| **Waitlist promotion**                  | Creates a meaningful event-ticketing workflow without huge scope   |
| **Order / Payment / Ticket separation** | Much cleaner domain model and easier failure handling              |
| **Event state machine**                 | Prevents invalid transitions and demonstrates business-rule design |
| **Event-level staff permissions**       | Shows granular authorization beyond simple roles                   |
| **Atomic concurrent check-in**          | Prevents two scanners admitting the same ticket                    |
| **Durable notification/outbox pattern** | Prevents emails/jobs from being silently lost after crashes        |
| **Failure-focused integration tests**   | Demonstrates production thinking rather than just CRUD testing     |
| **Price snapshot on OrderItem**         | Preserves historical truth even if ticket pricing later changes    |
| **Explicit DB constraints/indexes**     | Moves important correctness guarantees into the database           |
| **Server-authoritative pricing**        | Prevents client-side price manipulation                            |
| **Crash/retry payment scenario**        | Gives you a strong real-world Stripe interview story               |

## The new project philosophy

Instead of:

> **“I built many features.”**

the project becomes:

> **“I built a relatively focused event platform and solved several real backend consistency problems correctly.”**

The **five things to know extremely well** are:

**ticket inventory concurrency → Stripe webhook/idempotency → authorization → atomic check-in → failure/retry handling.**

Those are the areas I'd expect an interviewer to find substantially more interesting than another dashboard, filter, or CRUD screen.
